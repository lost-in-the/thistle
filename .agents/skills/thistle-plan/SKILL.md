# Plan

Use repository-relative paths from the checkout root. Read the assigned issue,
current claims, `docs/MISSION.md`, and the applicable sections of
`docs/development/agent-workflow.md`. Apply the assigned
[role](../../../docs/development/agent-team.md#roles); invoking this skill grants
no additional role or permission.

1. State the developer's question and observable answer. Preserve the evidence
   distinction between declarations, registered behavior, source candidates and
   observed execution. Identify what remains unknown.
2. Find existing work and accepted interfaces before creating scope. Check actual
   dependencies and candidate identities; a dated report does not establish them.
3. Choose the smallest useful vertical outcome. Name the shared interface owner,
   disjoint writer scopes, integration owner and acceptance owner. Separate code
   dependencies from scarce host resources.
4. Select the lowest meaningful checks plus required affected gates. Reuse
   fixtures, tools and applicable receipts. Distinguish scoped acceptance from
   launch qualification and publication.
5. Explain the cost of the chosen design: complete-workflow work, allocations,
   maintenance, security and accessible use. If repeated patches preserve a known
   limitation, propose a bounded refactor with a customer acceptance condition.
6. Give the PM a compact scope/acceptance/dependency proposal. Only the assigned
   PM updates planning metadata; a technical worker records its own bounded
   claim/evidence. Existing authorization covers routine implementation choices.

Return the outcome, scope, dependencies, named responsibilities, minimal evidence,
and next action. Escalate an actual product or authority choice with a concrete
recommendation. Continue independent authorized work while that choice is open.
