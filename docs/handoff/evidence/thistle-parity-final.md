## Basis for approval

The plan establishes the right competitive contract: the released Woods product is a minimum, the useful implemented capability in the pinned current repositories is also a target, and public launch requires the approved customer jobs to be complete. Internal prototypes do not satisfy that launch gate. A capability ledger must expose optional configurations, failure paths, coverage and untested cases, so a favorable average cannot conceal an omitted family or cohort.

It also preserves the owner's permission to rethink the product. Thistle has no obligation to reproduce old tools, command names, MCP schemas, Ruby APIs, filenames, URLs, screens or backend mechanics. Job-level comparator adapters belong in the independent testbed. The engine is newly implemented; Map code, design assets and branding can be reused. A single gem or one core plus an optional UI gem remains a delivery choice governed by actual dependency and operational cost.

These two principles are compatible in the candidate: preserve what users can reliably accomplish, while redesigning how they accomplish it.

## Required breadth is retained without prescribing a clone

The inventory covers the central distinction of Woods: runtime-resolved Rails and database facts plus source evidence. It also includes the application layers that a narrow rewrite could miss: asynchronous work, mail/templates/components, authorization and GraphQL, packages and external dependencies, configuration/infrastructure, tests/support, documentation/frontend context, and installed framework source.

The plan treats agent, human and programmatic users as consumers of shared evidence. It retains search and exact identity, relationships and flow limits, ranked retrieval, history/impact, observed traces, maintenance/freshness, exports, remote and offline operation, and external reader jobs. It does not require one legacy extractor class, tool or page for each capability.

The proposed persistent investigation is a legitimate alternative to a collection of disconnected pages. The candidate identifies its useful outcomes—start from a question, URL, symbol, file or change; follow evidence; choose a next step; retain and resume context—and tests total effort and correctness. Existing Map capabilities remain a baseline for comparison, not a novelty claim.

## Evidence and usability protections are adequate for the plan

Runtime reflection, static references, inference and observed execution remain distinct. Unknown, unavailable, incomplete, unresolved and failed outputs are preserved. The capture and incremental sections address source/runtime mismatch, negative dependencies, lost watcher evidence, multi-database scope, stale semantic overlays and last-good publication. Independent expected facts supplement full/incremental agreement, preventing a shared omission from passing both paths.

The naming design is appropriately framed as product accessibility and cognitive usability. It does not promise medical effectiveness, require a diagnosis, or equate fewer keystrokes with less effort. Recognition, consistent vocabulary, approximate wording, visible controls, interruption recovery and alternative input paths are explicit evaluation targets. Shortcuts are optional and must not corrupt ordinary text entry or exact target selection.

The source catalogue now includes the missing Map coverage and Guide qualification references, alongside the extractor, retrieval, reader, lifecycle, backend and testbed sources that support the parity inventory. The plan distinguishes documented capabilities, installed verification, proposed architecture and unproven claims.

## Approval boundary

This approval is for the design and launch approach represented by the exact hash above. It is not a certification that Thistle exists, has achieved parity, passes accessibility or security qualification, improves performance, or is ready to release. The candidate already requires those results through its ledger and independent launch gates; this review adds no new implementation gate.

Changes limited to approval metadata and recorded hashes can carry this approval forward. A semantic change to scope, parity classification, evidence guarantees, required customer jobs or launch gates requires another review of the changed candidate.
