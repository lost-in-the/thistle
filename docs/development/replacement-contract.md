# Complete application investigations

Thistle must replace the useful outcomes of Woods and Woods Map with an
independently implemented Rust engine, a faithful Ruby/Rails observation boundary
and an equal-or-better human and agent interface. This is a product contract, not
a description of features already accepted. Green components and merged slices
do not establish replacement quality. All 17 launch capabilities remain
unqualified until their declared outcomes and support scope have accepted
evidence.

## One product, authoritative evidence

Provide a coherent install, configure, capture, open Map and connect MCP path
using Thistle's own artifacts. No Woods process, index or engine gem is required.
Optional internal packages can isolate startup and dependency costs without
making the user assemble a second product. Console, a REPL and arbitrary
evaluation endpoints are outside scope.

Rust owns identities, validation, storage, queries and derived analysis. Ruby
may faithfully observe substantial Rails semantics in an explicitly supplied
loaded application; it is not limited to shallow reflection. Observation must
preserve ownership, inherited registration, conditions and unavailable context.
Map and MCP present supported Core answers rather than infer missing semantics.
Woods engine code is not reused. Authorized Map components retain provenance and
license attribution.

Distinguish source declarations, saved observations, resolved relationships and
actual execution. A static match is not runtime dispatch, a registered callback
is not an invocation, and an observed option is not a physical database
constraint. Preserve duplicate, generated, missing, partial and stale cases.
These distinctions are honest boundaries while authoritative semantics are
implemented, not permanent substitutes for useful Rails understanding.

## Two complete investigations

Feature planning must be possible through ordinary visible controls:

1. Find the model relevant to a proposed change and read its full admitted
   physical source, method outline and contribution ownership.
2. Inspect relevant physical schema, associations and lifecycle attachment
   points. Identify effective owners and callers where evidence supports them.
3. Follow the controller/action, permitted inputs, filters, render/view and
   template/layout relationships needed to plan the change.
4. Reach exact named physical Source witnesses and return with the saved
   generation, query, ordered selection and supported reading position intact.

Investigating an intermittent mailing failure must connect the actual questions:

1. Start from the creation path and distinguish conditional code from observed
   filter/callback registration and execution evidence.
2. Follow supported transaction, enqueue, job/queue, mailer/action and template
   witnesses, keeping asynchronous, dynamic and binding boundaries explicit.
3. Inspect template inputs, ownership and relevant mismatches, then use history,
   co-change or comparison evidence to assess a change hypothesis.
4. Preserve the evidence trail and produce a deliberate narrative handoff that
   a fresh recipient can use without reconstructing the investigation.

These are whole useful jobs, not page or extractor counts. A handler test,
protocol handshake or collection of links cannot stand in for an actual human
or agent completing the corresponding investigation.

## Required workbench breadth

The complete workbench includes:

- A Field Guide with as-written and effective/contributed lenses, physical
  source, named owners, callers and an understandable method outline.
- Physical schema and supported model relationships, plus authoritative
  lifecycle, controller-filter, callback, effect and asynchronous facts.
- Routes and selected-action Passage; readable job, mailer and template
  investigations with relevant evidence rather than generic save diagrams.
- Typed dependency/flow graphs at requested depths 1 through 3, named equivalent
  lists, architecture/Landscape views and whole-schema ERD where supported.
- Real history, commit/branch/range, co-change, diff, impact, relevant-test and
  since-change evidence, with independent source and relation coverage.
- Trail, notes, resumable investigation state, deliberate narrative handoff,
  exports and supported Ruby, Map and MCP interfaces over the same Core meaning.
- Optional contextual Guide only after these authoritative investigations work.

Saved-generation comparison does not complete commit/branch comparison. Resolve
revision selectors to immutable commit/tree/capture identities at preparation or
capture, preserving dirty-source provenance. Branches move, and the same commit
can have different captured payloads. Ordinary Map requests must not run Git or
mutate a user's checkout.

## Improve the original reading costs

Put useful answers before controls and diagnostics. Give physical source enough
width and space to read; avoid empty annotation tracks and small independent
scrolling panes. Make wrapping and disclosure deliberate and reversible without
losing content. Provenance, budgets and uncertainty must remain available in
purposeful disclosures without hiding important answer limitations.

Keep Find, Source, Links and Check recognizable. Find/search must be visible and
discoverable on every model screen, including narrow and keyboard entry. Support
ordinary links and forms without JavaScript, clear focus, text input and IME,
optional home-row shortcuts and a named accessible graph/list equivalent. Do not
depend on remembering commands or interpreting icon-only controls.

Use one canonical return context. Preserve generation, query, full ordered
selection, selected action/family/filter and supported physical position. Explain
an omitted query or unsupported position and offer an exact recovery path.
Missing generations refuse; they never silently substitute CURRENT. A scope URL
shares selected evidence, not the investigator's reasoning. Narrative handoff
must make its purpose and recipient context explicit and be checked with a fresh
recipient.

Preserve evidence meanings: default presence differs from its value, including
false, zero-like strings, empty strings and null. Rails configuration differs
from physical constraints; saved representations differ from distinct runtime
definitions. Graph and list labels must name the same Core-selected entities and
witnesses. No first-candidate binding or silent truncation may simplify an answer.

## Interoperability and cost

Requested focus-state and JSON interoperability requires an explicit versioned
mapping for typed identities, generations, ordering, null/unknown states,
continuation and refusal. Do not claim byte compatibility or force a storage
format merely because an original design used it. The older depth-1/2 graph
proposal with 300 nodes and 1000 edges needs an explicit disposition alongside
the requested depth 3; it is not permission to discard the deeper outcome.

Original targets such as a 300-node graph below 500 ms or a warm 3000-unit view
below 200 ms remain unmeasured goals. Response caps do not establish traversal,
heap or latency bounds. Compare complete useful work: install/build, startup,
capture, publication, Reader open and directory construction, invalidation,
querying, native crossings, allocations, rendering, repeated navigation and
retained storage. Do not assume that Rust or a faster inner loop improves the
complete job. Reuse maintained tools where their current fit is demonstrated;
custom code must earn its maintenance and downstream cost.

## Evidence and remaining work

Current bounded source slices do not complete this contract. Follow the exact
artifact/support tuple through focused native and Reader boundaries, installed
producer/fresh-consumer cards, actual MCP-client investigations and visible Map
tasks. Positive and negative cases must cover partial, duplicate, wrong-generation,
missing/stale, refusal and incomplete traversal outcomes. Captured text remains
data, not executable instructions or authority over a client.

Browser engine, keyboard, no-JavaScript, narrow layout, real zoom, IME,
assistive-technology and person evidence each retain their actual scope. Missing,
unrun, failed, cancelled or inconclusive evidence does not pass. Candidate CI,
integration, applicable user acceptance, launch qualification and publication
remain separate decisions. A useful public testbed can support designed edge
cases and integration work without granting private-app, credential or arbitrary
execution authority.
